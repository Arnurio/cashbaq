# ORCHESTRATOR.md — Гайд для CTO / Главного агента

> Этот файл читает тот, кто **управляет** командой агентов — не тот, кто пишет код.
> CTO-агент не программирует сам. Он декомпозирует, назначает, проверяет, сводит.
>
> Связанные файлы: [AGENTS.md](AGENTS.md) (механика агентов) · [SUBAGENTS.md](SUBAGENTS.md) (субагенты)

---

## РОЛЬ ОРКЕСТРАТОРА

Оркестратор — это **главный агент** (обычно первый аккаунт / главное окно Claude Code).

Он решает:
- Какую задачу нужно сделать прямо сейчас
- Как разбить её на изолированные куски
- Кому отдать каждый кусок
- Как проверить результат
- Как собрать всё вместе без конфликтов

Он **не делает сам**:
- Не пишет код напрямую (исключение: 1-строчные правки)
- Не читает 500-строчные файлы целиком
- Не разбирается с деталями реализации — только с интерфейсами между кусками

## ФРЕЙМВОРК ДЕКОМПОЗИЦИИ

### Шаг 1: Определи границы изменений

Перед декомпозицией ответь на вопросы:

```
1. Какие файлы затронет задача?
2. Есть ли между ними зависимости (A использует B)?
3. Можно ли разделить так, чтобы каждый агент работал в своих файлах?
4. Что должно быть готово первым (блокирует других)?
```

### Шаг 2: Выбери паттерн декомпозиции

**Паттерн "Слои" (подходит для большинства фич):**
```
Агент-1: Типы + API (lib/types.ts, lib/api.ts)   ← делает первым
Агент-2: UI мобилки (app/)                        ← ждёт Агента-1
Агент-3: Admin panel (admin/src/)                 ← независим
```

**Паттерн "По фиче" (несколько независимых фич одновременно):**
```
Агент-1: Фича A (целиком — типы + UI)
Агент-2: Фича B (целиком — типы + UI)
Условие: фичи не трогают одни и те же файлы
```

**Паттерн "Исследование + реализация":**
```
Субагент Explore: найди все места где используется X
CTO анализирует результат
Агент-1: реализует изменение в найденных местах
```

### Шаг 3: Запись в AGENTS.md

После декомпозиции — обнови таблицу задач в [AGENTS.md](AGENTS.md):

```markdown
| Агент | Ветка | Задача | Файлы | Статус |
|-------|-------|--------|-------|--------|
| Агент-1 | feature/types-update | Добавить тип X в types.ts | lib/types.ts | 🔴 |
| Агент-2 | feature/ui-screen | Показать X на главном экране | app/(tabs)/index.tsx | 🔴 |
```

## ПОРЯДОК РАБОТЫ ЗА СЕССИЮ

```
1. Прочитай HANDOFF.md           → понять состояние проекта
2. Прочитай STRATEGY.md          → выбрать приоритет
3. Сформулируй цель спринта      → одно предложение
4. Декомпозируй (фреймворк выше) → 2-5 подзадач
5. Запиши в AGENTS.md            → обнови таблицу
6. Выдай промпты агентам         → (шаблон в AGENTS.md)
7. Жди результата                → агент пушит ветку
8. Принимай работу (merge)       → проверь тесты
9. Обнови HANDOFF.md             → запиши что изменилось
```

## КАК ПРИНИМАТЬ РАБОТУ АГЕНТА

```bash
# 1. Забери ветку
git fetch origin
git checkout feature/agentN

# 2. Проверь что изменилось
git diff main...feature/agentN --stat   # список файлов
git diff main...feature/agentN          # детали

# 3. Запусти тесты
npx jest
npx tsc --noEmit

# 4. Быстрая визуальная проверка (web)
npx expo start --web

# 5. Если всё ок — merge
git checkout main
git merge feature/agentN --no-ff -m "merge: [описание задачи]"
git push origin main

# 6. Если конфликт — реши и скажи агенту что произошло
```

## РАЗРЕШЕНИЕ КОНФЛИКТОВ

Конфликты возникают когда два агента тронули один файл. Правило:

```
Конфликт в lib/types.ts — CTO решает вручную:
  - Взять оба изменения (чаще всего правильно)
  - Убедиться что новые типы не ломают друг друга
  - Запустить tsc после merge

Конфликт в package.json — взять объединение зависимостей

Конфликт в app/_layout.tsx — осторожно, это root layout
```

**Профилактика конфликтов:** перед выдачей задачи проверяй что файлы в разных зонах (`AGENTS.md`, секция "Зоны ответственности").
